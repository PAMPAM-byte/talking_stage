# Stage 12 account deletion contracts

10 October 2026 · Local active-data deletion; hosted retention policy remains pending.

The Settings account page now connects the accepted typed `DELETE` and final-confirmation flow to a real account deletion operation. Current-password verification obtains a fresh session before deletion. The server derives the account email/ID from verified Auth and accepts neither from the browser. The database additionally requires completed adult access, exact confirmation, a token issued within five minutes, and an explicitly enabled deployment configuration. Anonymous and service-role calls cannot execute this RPC.

`delete_own_account` locks the owner and owned conversations and removes data in one transaction: reply jobs, AI and summary reservations, summaries, all memories including previously soft-deleted facts, memory preferences, report resolutions, report evidence, reports, messages, conversations, personal AI-usage rows, Auth identity/sessions and profile. Request limits cascade with Auth deletion. Deleted report references and actor IDs are removed from technical admin audit rows. Shared character assets and anonymous project spending totals remain. A database failure rolls the transaction back; late reply/summary commits cannot insert into removed jobs or conversations.

Accounts with any payment intent, administrator role, cast-review/publication attribution or moderation-resolution attribution are refused without changing data. These need a separately approved retention and operator handoff process. No payment/legal retention duration is invented here. The local erase-all behavior follows the accepted mock contract for ordinary accounts and their submitted reports; it is not approval of a hosted moderation-evidence exception.

After successful deletion, the server clears local auth/flow cookies. A full document navigation to `/account-deleted` discards the prior React route tree. Existing remote sessions have no Auth user/profile and cannot access owned data. Password failures retain confirmation input; availability and backend failures have explicit recovery. A network failure can leave the result uncertain, so the server asks users to sign in again to check rather than claiming an unconfirmed deletion failed.

The migration defaults account deletion to **disabled**. `npm run backend:deletion` enables it only against loopback Supabase and the named local database. Hosted enablement, provider/backup retention, policy review and restoration controls remain launch prerequisites. Existing backups are not erased or given a fictional expiry by this slice. The UI states that they may still contain deleted data. No claim of total erasure from backups or from a provider request already sent is made.

Runbook: back up before migration; run the database and authenticated browser checks; enable only the local configuration; do not restore a historical backup into a user-accessible environment without reapplying deletions. The subsequent [local backup slice](./stage-12-backup-contracts.md) adds an atomic suppression journal, signed ledger and isolated restore replay. The owner-approved seven-day managed-backup expiry policy is enabled locally. Hosted ledger durability, retention and recovery approval remain prerequisites before hosted deletion is enabled.

Validation commands: `npm run test:account-deletion`, `npm run test:reports-database`, and the authenticated `account-deletion.spec.ts` browser check. Database coverage includes wrong confirmation, old tokens, disabled configuration, roles, financial/operator guards, rollback after an injected failure, every erased table, other-user preservation and late-job rejection. Browser coverage uses a disposable account, wrong-password recovery, cancellation, successful erasure and refusal of old sign-in/session access.
