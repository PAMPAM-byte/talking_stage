# Reply latency and recovery

## Additional speed work — 20 October 2026

Thread metadata reads now run in parallel after the owned conversation is loaded, and empty payment/photo/delivery lookups are skipped. The protected wrapper and thread share a React render-scoped account reader, following the installed Next authentication guide. The uncached reader remains in mutations so session changes stay fresh; account data is never cached across requests or users.

A read-only local Chromium/Edge sample loaded the same existing conversation four times per run, discarding the warm-up and reporting the remaining three navigation-to-composer measurements. Before: 3,040 / 3,279 / 3,582ms (median 3,279ms). After: 2,459 / 2,457 / 2,356ms (median 2,457ms), approximately 25% lower. These are small local development samples over the hosted database, not a controlled production benchmark or measured AI-generation improvement. No message was submitted and no model call was made by this benchmark.

The reply JSON schema is now independent of character photo IDs and photo availability. Available photos remain in the character context and every selected ID must still pass server validation and database publication/ownership checks. Request amounts retain runtime and database bounds; unsupported numerical constraints were removed from the provider schema. This lets equivalent conversations reuse the same output grammar instead of supplying per-character ID enums. [Anthropic documents first-schema compilation latency and grammar caching](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#grammar-compilation-and-caching); actual provider-side savings have not been measured. Offline Claude tests check identical schemas with and without photos and rejection of unadvertised IDs. Provider, photo/database, reply/action/access-boundary, payment, TypeScript and scoped ESLint checks cover the changes.

20 October 2026. The reported Retry reply / Skip reply controls are recovery for a saved user message whose generation did not complete. An aggregate read-only audit found 165 completed jobs and one failed `provider_error` among jobs created in the preceding two days. That code does not establish the exact provider HTTP error. No private message text was printed.

The send action previously revalidated the entire message layout before the response completed. That could trigger another server render with account/thread/asset reads before `after()` started generation. Send now returns its saved ID without that revalidation; the durable outbox and metadata sync reconcile it. The background task revalidates after processing the reply, before optional summary work. A boundary regression test checks this ordering. Generation still depends on database and provider latency; no new end-to-end provider timing claim is made.

The client previously marked Seen when save succeeded and treated every watched job as typing. It now distinguishes waiting from actual generation: queued messages show one tick and Preparing a reply; confirmed generating jobs show typing and double ticks. Completed and previously attempted server jobs retain durable Seen behavior. A cancelled or failed generation does not undo a real receipt. Observation starts after 150ms instead of one second, without increasing the steady polling frequency. Explicit retries retain the same job and lease/budget checks; failures are not automatically replayed.

The generic floating reply-failure toast is removed. Recovery controls beside the message have a short explanation that the message is saved. Reply GET and POST now use strict account availability checks, preserving 503 retry behavior for identity outages instead of incorrectly reporting 401 and navigating to sign-in. Provider telemetry records only allowlisted outcome categories and duration, never prompts, messages, credentials or response bodies; diagnostic sink failure cannot fail the reply.

Automatic approval review rejected a proposed retry of the existing failed conversation because it would resend private conversation context to the external provider without specific approval. That command was not run, and no alternate path was used to retry it. Exact live-provider diagnosis and recovery of that old job remain pending that approval or the user's own explicit Retry reply action. Synthetic provider, database, API-boundary and browser tests do not establish live provider recovery.

Validation: all 12 chat delivery browser cases passed, including queued-to-generating receipt timing, late completion, reopening, interruption, draft preservation and saved-message isolation from reply failure. TypeScript, scoped ESLint, provider, reply integration, reply recovery, API boundaries and monitoring checks passed. All generation tests used synthetic/injected providers; no live AI request was made during this work.
